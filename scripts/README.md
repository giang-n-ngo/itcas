# Cluster (Slurm) submission

> Operator-only docs. Slurm is our specific cluster workflow, not a universal
> standard, so these instructions live here rather than in the released
> top-level `README.md`.

GPU sweeps are driven by a JSON job spec (`scripts/jobs.json`). Jobs can be
provided explicitly in `jobs.separate` and/or generated by cartesian expansion
in `jobs.group`.

- `jobs.separate`: explicit list where each entry is **one Slurm job**.
- `jobs.group`: each entry expands into multiple jobs by combining options
  (`methods x problems x difficulties`), while `quality` is only combined for
  `method=itcas`.

Each resulting job is one `(method, problem, difficulty[, quality])` run over a
seed range on a **single GPU**, executing `n_concurrent` seeds at a time and
iterating batches until the range is complete (already-finished seeds are
skipped, so jobs are safe to requeue):

```jsonc
{
  "defaults": { "device": "cuda", "results_root": "results/sweep",
                "n_concurrent": 4, "thresholds_path": "configs/thresholds.json",
                "experiments_path": "configs/experiments.json" },
  "jobs": {
    "separate": [
      { "method": "itcas", "quality": "roi_mi", "problem": "sphere2_6d", "difficulty": 0.1,
        "seeds": "0-9", "n_concurrent": 4 }
    ],
    "group": [
      {
        "methods": ["itcas", "random"],
        "problems": ["sphere2_6d", "dtlz2_6d"],
        "difficulties": [0.1],
        "quality": ["roi_mi", "lf_mi"],
        "seeds": "0-9",
        "n_concurrent": 4
      }
    ]
  }
}
```

In the group example above, generated jobs are:
- `itcas x sphere2_6d x 0.1 x roi_mi`
- `itcas x sphere2_6d x 0.1 x lf_mi`
- `itcas x dtlz2_6d x 0.1 x roi_mi`
- `itcas x dtlz2_6d x 0.1 x lf_mi`
- `random x sphere2_6d x 0.1`
- `random x dtlz2_6d x 0.1`

`jobs.json` only selects the **sweep matrix** (`method` x `problem` x
`difficulty` x `seeds`, plus `quality` for `itcas` variants). The run **sizing**
(`budget`, `batch_size`, `n_init`)
is problem+difficulty dependent and lives in
[`configs/experiments.json`](../configs/experiments.json), resolved per field as
`problems[<problem>][<difficulty>]` -> `problems[<problem>].defaults` ->
top-level `defaults` (the `<difficulty>` key is the `threshold_pct` string, e.g.
`"0.05"`, or `"defaults"` for uncalibrated runs). Edit that file — owned by the
Scientific Coder — to tune sizes per problem/difficulty; `jobs.json` stays sizing-free. For `itcas`, `quality` is part of the run
identity, so ROI-MI and LF-MI are written to separate output directories.

## Valid `method`, `problem`, and `difficulty` values

These are the exact strings to put in `scripts/jobs.json` (and to pass to
`--method` / `--problem` / `--threshold_pct` on the CLI). They are owned by the
Scientific Coder; this table is a convenience snapshot — the source of truth is
the code registries, so re-check them if a job errors with `Unknown method` /
`Unknown problem`.

**`method`** (from `itcas.baselines.REGISTRY` + the proposed algorithm). Grouped
per `contexts/fair_lse_comparison.md`'s benchmark-matrix families: **A** =
Direct Active Search, **B** = Pure Level Set Estimation, **C** = Two-Stage
LSE-then-Sample. Any method ending in `_batch` is the DPP-diversified batch
sibling of its base method (built with `itcas.algorithms.qd_dpp`) and, like
`itcas`, honors `batch_size` — every other (sequential) method runs exactly
one evaluation per iteration regardless of `batch_size`.

| `method` | Status | Notes |
|----------|--------|-------|
| `itcas` | proposed | Always batch (`batch_size` > 1 honored); quality via `--quality` (`roi_mi`\|`efig`\|`edig`\|`ndig`). |
| `random` | baseline (A) | |
| `random_batch` | baseline (A) | DPP-batch sibling of `random`: uniform quality, pure space-filling diversity. |
| `one_step` | baseline | One-step active search. |
| `ez` | baseline | EZ mutual information. |
| `eisr` | baseline | |
| `cas_eci` | baseline (A) | Uses input-space `radius`. |
| `cas_eci_batch` | baseline (A) | DPP-batch sibling of `cas_eci`. |
| `moc_cas_hard` | baseline (A) | Uses objective-space `obj_radius`. |
| `moc_cas_hard_batch` | baseline (A) | DPP-batch sibling of `moc_cas_hard`. |
| `moc_cas_soft` | baseline | Uses objective-space `obj_radius`, soft probit gate. No `_batch` sibling. |
| `straddle` | baseline (B) | Single-objective LSE formula extended via **round-robin objective alternation**: iteration `t` scores only objective `t % m` (not an aggregate over all objectives). |
| `straddle_batch` | baseline (B) | DPP-batch sibling of `straddle`; same alternation rule. |
| `c2lse` | baseline (B) | Confidence-based Continuous LSE (continuous acquisition, `itcas`'s multistart machinery under the hood). Same round-robin alternation as `straddle`. Ignores `--quality`. |
| `c2lse_batch` | baseline (B) | DPP-batch sibling of `c2lse`. |
| `bes` | baseline (B) | Binary Entropy Search (continuous, Gauss-Hermite quadrature). Same round-robin alternation. Ignores `--quality`. |
| `bes_batch` | baseline (B) | DPP-batch sibling of `bes`. |
| `straddle_then_sample` | baseline (C) | Runs `straddle` for `t < 0.5*T`, then switches to combined-uncertainty interior sampling soft-constrained to joint PoF ≥ 0.95 for the rest of the budget. |
| `straddle_then_sample_batch` | baseline (C) | `_batch` sibling; honors `batch_size` in both stages. |
| `c2lse_then_sample` | baseline (C) | Two-stage wrapper around `c2lse`, same schedule as `straddle_then_sample`. |
| `c2lse_then_sample_batch` | baseline (C) | `_batch` sibling. |
| `bes_then_sample` | baseline (C) | Two-stage wrapper around `bes`, same schedule as `straddle_then_sample`. |
| `bes_then_sample_batch` | baseline (C) | `_batch` sibling. |
| `eps_constraint` | **placeholder** | Raises `NotImplementedError` — do **not** submit. |
| `moo_cluster` | **placeholder** | Raises `NotImplementedError` — do **not** submit. |

> **RMILE** (Robust Maximum Improvement for LSE, the fourth Family-B/C
> baseline in the plan doc) was implemented and then **removed** — its
> per-candidate joint-posterior-covariance solve over a ~1000-point reference
> pool was too expensive to keep in the sweep. Do not add `rmile*` to
> `jobs.json`; it is not in `itcas.baselines.REGISTRY`.

**`problem`** (from `itcas.pipeline.PROBLEM_REGISTRY`):

| `problem` | Dim (d_x + d_w) | Objectives | Role |
|-----------|-----------------|------------|------|
| `sphere2_6d` | 6 (3+3) | 2 | Benchmark 1 — shifted sphere (convex sanity check). |
| `rosenbrock_sphere_6d` | 6 (4+2) | 2 | Benchmark 2 — contextual Rosenbrock vs. sphere. |
| `multimodal_trap_20d` | 20 (10+10) | 3 | Benchmark 3 — rugged high-D stress test. |
| `dtlz2_6d` | 6 (3+3) | 4 | Benchmark 4 — contextual DTLZ2. |
| `two_circles_2d` | 2 | 2 | Smoke test only (no calibrated thresholds). |
| `contextual_circles_3d` | 3 (2+1) | 2 | Smoke test only (no calibrated thresholds). |

**`difficulty`** = the joint-feasible fraction `threshold_pct`. Calibrated
levels currently present in `configs/thresholds.json` for the four benchmarks:
`0.2`, `0.1`, `0.05`, `0.01` (smaller = harder). The two smoke-test problems are
**not** calibrated; for those, omit `difficulty`/`thresholds_path` and the
problem's built-in default thresholds are used. To add a level, run
`scripts/calibrate.sbatch <problem>` (see below).

## Scripts

Operator-owned; they wrap the Python entry points, no science inside:

| Script | Kind | Purpose |
|--------|------|---------|
| `scripts/install_env.sbatch` | GPU job | Build/verify the `itcas` conda env (installs a CUDA-matched torch, runs smoke tests, fails if the GPU is unusable). |
| `scripts/calibrate.sbatch`   | CPU job | Calibrate thresholds for **one** problem across **all** difficulty levels → `configs/thresholds.json`. |
| `scripts/submit.sh`          | wrapper | Read the JSON, size the array, submit the sweep. |
| `scripts/submit_jobs.sbatch` | array   | One array task per job = 1 GPU (`--gpus=1`), `n_concurrent` seeds at a time. |
| `scripts/run_seedset.sh`     | launcher| Runs one job set: drains pending seeds N-at-a-time, retries, optional email. |
| `scripts/summarize.sbatch`   | CPU job | Render per-problem summary PDFs (`itcas.summarize`) from completed runs. |

All scripts resolve the repo via `SLURM_SUBMIT_DIR` (Slurm copies `.sbatch`
files to a spool dir, so submit them **from the repo root**). They activate the
env with `module load Anaconda3; conda activate $CONDA_ENV` and export
`PYTHONNOUSERSITE=1` so the env's CUDA torch is used instead of any `~/.local`
build.

## 0) One-time: build the conda env (GPU job)

```bash
sbatch scripts/install_env.sbatch                  # creates/updates env 'itcas'
```

Defaults to the **cu124** torch wheel (the cluster's NVIDIA driver is CUDA 12.7;
the default PyPI wheel is CUDA 13.0 and would NOT see the GPU). Override the
build if needed:

```bash
sbatch --export=ALL,CONDA_ENV=itcas,TORCH_INDEX_URL=https://download.pytorch.org/whl/cu121 \
       scripts/install_env.sbatch
```

Verified result: `torch 2.6.0+cu124`, `torch.cuda.is_available() = True` on a
Tesla V100. Overrides: `CONDA_ENV`, `PYVER`, `CONDA_MODULE`, `TORCH_INDEX_URL`,
`REQ_FILE`.

## 0b) Calibrate thresholds (CPU job)

```bash
sbatch scripts/calibrate.sbatch sphere2_6d         # all difficulty levels
```

Runs on `--partition=cpu --qos=cpu` (Monte-Carlo sampling, no GPU). Overrides:
`PERCENTAGES`, `N_SAMPLES`, `SEED`, `OUT`, `CONDA_ENV`.

## 1) Submit the sweep

```bash
# Preview the array sizing / sbatch command without submitting:
DRY_RUN=1 CONDA_ENV=itcas scripts/submit.sh scripts/jobs.json

# Submit (partition defaults to 'gpu', 1 GPU/job, throttled to MAX_GPUS=2):
CONDA_ENV=itcas scripts/submit.sh scripts/jobs.json
```

Defaults follow the cluster format: `--partition=gpu`, `--gpus=1`,
`--qos=batch-short`, `--time=1-00:00:00`, array throttle `%MAX_GPUS` (=2, the
per-user GPU cap). Override via env: `PARTITION`, `GPUS` (e.g. `v100:1`), `QOS`,
`TIME`, `MAX_GPUS`, `ACCOUNT`, `CONDA_ENV`.

## Logs & monitoring

Slurm logs: `slurm_logs/<job>-%A_%a.{out,err}`; per-seed console logs:
`<results_root>/<problem>/<diff>/<method>/*.run.log`.

```bash
squeue --me                          # queue state of your jobs
sacct -j <jobid> --format=JobID,JobName%20,State,ExitCode,Elapsed,NodeList
seff <jobid>                         # resource efficiency after completion
scancel <jobid>                      # cancel a specific job/array task
```

## 2) Summary visualization (CPU job)

After (some of) the sweep has finished, render per-problem summary PDFs that
aggregate per-seed metric *areas* into horizontal boxplots — one row per
difficulty, one column per metric (`#positives` area-above + 3 fill-distance
areas + a hypervolume column = product of those areas).

```bash
# Default: every problem found under results/sweep, PDFs to results/sweep/_summary/
sbatch scripts/summarize.sbatch

# Restrict to one problem:
sbatch --export=ALL,BENCHMARK=sphere2_6d scripts/summarize.sbatch

# Custom input/output:
sbatch --export=ALL,INPUT_DIR=results/sweep,OUTPUT_DIR=results/sweep/_summary \
       scripts/summarize.sbatch
```

Runs on `--partition=cpu --qos=cpu` (matplotlib + trapezoidal integration, no
GPU). Overrides: `INPUT_DIR`, `OUTPUT_DIR`, `BENCHMARK`, `CONDA_ENV`,
`CONDA_MODULE`. Output PDFs:

```
<OUTPUT_DIR>/<problem>_summary_vs_evaluations.pdf
<OUTPUT_DIR>/<problem>_summary_vs_steps.pdf
```

It is safe to re-submit at any time — existing PDFs are overwritten with the
current set of completed seeds. The companion per-iteration line plots
(`itcas.visualize`) are still emitted automatically at the end of each sweep
job and live next to the runs under `<results_root>/<problem>/<difficulty>/`.
